## 设计要点（沿用 T09 语义，不新增策略）

MCP 层只是传输：每次 `tools/call` 都经**同一个** `StrategySession`，因此白名单、run 作用域、
预算门（8 次工具调用）、截止时间、证据登记、错误码与证据载荷与进程内 `ProtocolTools` 门面逐项
一致。回归 `test_receipts_match_the_in_process_facade` 在两个独立但相同的后端上逐工具比对
`evidence_ids`、证据记录、`duplicate` 与最终会话计数。

- **只暴露六工具、没有提交工具**：最终提交仍走 §10.5 协议（`test_no_submission_tool_exists_on_the_mcp_surface`）。
- **能力只收窄**：`--tools` 子集裁剪工具列表；未知工具在启动时拒绝（`_parse_allowlist`）；
  场景关系白名单仍由后端证据工具强制（`raw_customers` 被拒时收据保留 `RELATION_NOT_ALLOWED`）。
- **单 run 串行化**：`ToolGateway` 的 asyncio 锁让并发请求按序执行——8 个并发调用恰好计 8 次尝试、
  同一记录只登记一次、`request_id` 序号 1..8（`test_concurrent_requests_are_serialized_and_counted`）。
- **无额外能力**：不提供 dbt CLI、SQL、管理命令或通用文件系统访问；服务进程只持有该 run 的会话。
- **断连不影响 harness**：传输关闭后会话状态一致且仍可继续被 harness 使用
  （`test_disconnect_does_not_corrupt_the_session`）。

## 过程中修正的两点

- `serve_stdio` 起初直接调用 `run_stdio_async()` 而忘记 await，示例客户端首次运行以
  `Connection closed` 失败；改为 `asyncio.run(...)` 后通过。此问题由真实子进程链路暴露，
  进程内测试发现不了。
- 计数口径在实现中被固定下来并写入规范：**未知工具与越权工具在门外免费拒绝**，而"工具名合法
  但参数/run 作用域非法"以及后端拒绝**都计一次尝试**（`test_wrong_run_and_refused_relation_keep_their_codes`
  断言 `tool_call_attempts == 2`，规范 §3 同步）。

## 审计整改（第一轮，2026-09-16）

- **MCP 参数校验绕过统一收据与计数（P1）**：初版把工具注册在 `FastMCP` 上，SDK 的入参模型在进入会话前
  就拒绝缺参请求（SDK 错误、无收据、计数 0），网关又清洗参数、丢弃多余字段、把非字符串替换成空串
  （多参因此返回 `accepted=True`）。现改为 SDK 低层 `Server` + `call_tool(validate_input=False)`：
  `tools/list` 只声明契约（规范参数名、`string`、`required`、`additionalProperties: false`），
  **入参原样投递**给会话；同时把 `ToolRequest.arguments` 放宽为原始映射，让类型错误在两条路径上都成为
  收据而不是构造期异常。回归（逐项比较拒绝码、收据与计数，各 5 个用例）：
  `test_argument_errors_reach_the_protocol_receipt_path`（缺参、多参、类型错误、另一个工具的缺参、
  组合缺参）——MCP 与进程内直接调用都得到 `TOOL_ARGUMENT_INVALID`、`tool_calls_used == 1`、
  会话计数一致，且被拒后会话仍可用；`test_advertised_schema_documents_the_canonical_arguments`
  钉住对外声明的契约；`test_unknown_tool_is_an_mcp_error_not_a_receipt` 钉住未知工具名仍是
  MCP 工具错误（`isError=true`、不计尝试、无收据）。
