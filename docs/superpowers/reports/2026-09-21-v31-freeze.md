#### 3.7.2 根因再定位与修复（2026-09-21，委托方裁定后）

**§3.7 的机制描述不完整**：当时把根因写成「scripted 模型写死 `seed.*` 字面量」，据此方向应当是
改脚本。委托方裁定「修脚本节点选择、保留成功断言」后，我按该方向核查节点来源，发现**该方向不成立**
——真正的缺陷在**产品代码**：

- 用 `pipeline build` 物化 dbt catalog 后核对：`seed.jaffle_shop.raw_payments` **确实在目录内**
  （catalog 28 项），因此它**本应**被 kernel 接受。`lineage_node_candidates` 的语义是
  「subjects 中恰为 catalog 键者」，本案例的候选集**非空**。
- 但 agent 侧以 `getattr(self._tools, "lineage_node_candidates", None)` 解析该投影
  （`diagnostic_agent.py:2653`），不可调用时**退化为空元组**。而 `DiagnosisRunner.for_run` 在未显式
  注入 `tools` 时（`:2588–2600`）会把 `EvidenceTools` 包进 `StrategySession` 并改用
  `session.tools_facade()` ——该门面 `ProtocolTools`（`strategy_adapter.py:647`）**只实现六个协议
  工具方法，未转发 `lineage_node_candidates`**。于是候选集恒为空，kernel 对**任何**节点都以
  `NODE_ARGUMENT_NOT_PROVEN` 拒绝，脚本每次收到同一拒绝后重发同一调用，直至预算耗尽。
- 这解释了全部八例（均为 DIAGNOSTIC_KERNEL，且均表现为 `successful_tool_calls=1` 后死循环），
  也解释了为何它们**早于提交门**：该门面缺口自 `ProtocolTools` 引入即已存在。

**修复**（`fc9cb74`）：在 `ProtocolTools` 上补一个语义等价的只读转发——该投影**不是协议工具**
（不耗预算、不登记证据、不产生收据），故不走 `_call`：

```python
def lineage_node_candidates(self, subjects: tuple[str, ...]) -> tuple[str, ...]:
    resolver = getattr(self._session._tools, "lineage_node_candidates", None)
    return tuple(resolver(subjects)) if callable(resolver) else ()
```

**验收（全部通过）**：

| 检查 | 修复前 | 修复后 |
| --- | --- | --- |
| 单例 `DIAGNOSTIC_KERNEL-duplicate_payment_coupon_a` | FAILED（`MODEL_REQUEST_LIMIT`） | **`1 passed`**（67.0 s） |
| 全量 `tests/e2e/test_p1_policy_matrix.py` | `8 failed, 30 passed` | **`38 passed`**（39:17） |
| `tests/unit -q` | `1089 passed, 5 skipped` | `1089 passed, 5 skipped`（无回归） |
| `ruff check .` | clean | clean |

八例**全部转绿且成功断言未被放宽**——这些用例仍验证完整诊断链。**修复方向由「改脚本」改为
「补门面」**，依据是证据表明脚本的节点选择并无不妥（该节点合法）；改脚本反而会掩盖真实缺陷。
