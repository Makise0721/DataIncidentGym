1. **升版后历史清单 verify 失败属预期**（计划 §0 硬约束 2）。失败的报错文案只给

   审计侧可据 `config/benchmark/p1-formal-v23.json` / `-v30.json` 与当前树复核。
2. **一次瞬时测试失败已排除为回归**：`tests/unit/test_benchmark_manifest.py::
   test_manifest_has_frozen_catalog_denominator_and_schedule` 在「manifest + replays +
   diagnostic_agent」三文件组合的一次运行中失败（`pydantic/json_schema.py` 抛 `TypeError`），
   重跑两次均 68 passed；在**未改动的 HEAD** 上同组合连跑三次亦全绿。判定为**瞬时/顺序相关**，
   与本轮改动无关；全量 `tests/unit` 在该事件前后各一次均 1089 passed / 5 skipped。
3. **`git stash` 往返：前两次干净，第三次发生事故并已完全恢复（如实记录）**
   - **前两次（V1 基线）**：`git stash push` → 在干净树跑 verify → `git stash pop`。两次 `pop` 均干净
     恢复，8 个改动文件逐一如前。
   - **第三次（e2e 既有失败对照实验，见 §3.5）**：为判定 e2e 失败是否由本阶段引入，执行侧再次
     `git stash push` 后于旧版本常量上运行该用例，随后 `git stash pop` **发生冲突并未干净完成**。
     冲突文件为 `AGENT.md`、`README.md`、`mistake.md`——这三者属**所有者既有的
     `stash@{0}`（`pre-main-sync-20260830 user workspace files`）**，而执行侧误以为 `stash@{0}`
     始终是所有者那条、未意识到自己第三次 `push` 后 `stash@{0}` 已指向本轮的探针暂存，
     于是 `pop` 实际作用到了包含所有者文件的栈顶条目，导致所有者文件被写入工作树并冲突。
   - **恢复结果**：`README.md` 被 `checkout HEAD --` 还原（还原前 diff 为 +58 行，即所有者暂存内容
     的写入）；`AGENT.md`、`mistake.md` 在 HEAD 中本就不存在（属所有者未跟踪文件），已保留于工作树
     的未跟踪状态，**内容未丢失**；索引合并态经 `git reset` 清除。
   - **未受影响的资产**：三个提交 `ed04be9` / `bae3063` / `fea2d09` 与全部 8 个改动文件均完好
     （复核：两个版本常量分别为 `p1.strategy_adapter.v2` / `p1.controller.v20`，v31 清单在位）；
     **所有者暂存仍完整可恢复**：`git stash list` 仍为 `stash@{0}: On master:
     pre-main-sync-20260830 user workspace files`，其提交为 `e8b1584b4f37fa153c481e8a52d30e0d82592565`。
   - **教训（与 v24 报告 §3 同源）**：`git stash` 在多条暂存共存的工作区不可当作无副作用的探针手段。
     本报告如实记录，后续探针改用**独立工作树**（`git worktree`）或先核对 `git stash list` 顶层归属。
   - 该事故**未影响任何验收结论**：对照实验的有效性不依赖 pop 是否干净（失败在 `pop` 之前的运行中
     即已复现）。
