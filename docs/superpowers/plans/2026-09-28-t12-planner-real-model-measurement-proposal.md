# T12 规划器真实模型测量预登记方案（设计稿，2026-09-28）

状态：待审核；本文只规定实验与实施验收，**不授权**改代码、冻结身份、调用模型或启动 benchmark。规划器已有离线回归及四个 dev 变体的确定性真实 DB/dbt 闭环；这些结果不回答真实模型是否会执行规划，也不构成质量收益。

## 1. 问题与边界

问题是：在同一模型、公开任务、六个只读取证工具和基础预算下，`EVIDENCE_PLANNER` 的真实模型整格结果相对于当前 `DIAGNOSTIC_KERNEL` v18 如何？`STATIC_SKILL` 提供第二个同期基线。三者是**不同策略**；规划器额外有独立的两次计划拒绝预算，模型看见的是两个动作工具和一个终态输出工具，故不能写成“只有 prompt 不同”或“完整预算条件相同”。

所有样本都是已用于开发的 dev 场景；本实验不估计未见场景泛化，不对 v19 重新作采用判断。T13 的公开列证据 v2 工具不进入本实验，三策略仅访问原六工具及对应的公开上下文。历史 manifest、归档、评分与 v18 默认提示不改。

## 2. 先决实现：独立实验身份

现行 `p1.benchmark_manifest.v1` 强制六策略、12 个固定正式场景、106 格及 `p1-formal-vN` 名称；`benchmark_report.py` 也强制 106/94/12 并把主报告写死为 Static/Kernel。因此**不得**通过修改 v1 的六策略常量、借用某个策略槽位或手改 JSON 来安排规划器。

实施一个独立的 `p1.planner_comparison_manifest.v1` 实验合同，身份命名空间为 `p1-planner-compare-vN`。它在冻结时固定：实现修订、场景摘要与准入身份、三份完整政策面（含规划器 prompt、controller、模型可见工具描述/schema）、模型和端点配对、evaluator/result-inputs 摘要、基础预算及规划器附加预算、明确的 108 格顺序与派生 run ID。v1 loader、`generate_cells`、旧 ID 注册表及其历史验证结果保持原合同；新旧 schema 显式分派，旧 JSON 不迁移。

复用既有 doctor、ledger、恢复、六文件与 scoring-inputs 严格重载、滚动暂停及只读 partial 分析时，必须用新 manifest 的预期格数和策略集合验证，不能沿用报告里的 106/94/12 常量。新实验报告复用 T07 的 evaluator 同源指标与 T08 的完整组可靠性计算；新增规划器计划轨迹指标只读归档。若复用现有运行器需要抽出共享接口，先做不改变 v1 行为的窄改动，不复制第二套评测/成功判定。

冻结前补齐以下可执行验收：

1. v1 历史清单在其原身份上的严格加载和 verify 不退化；新合同拒绝跨版本 ID、替换的策略/场景/run ID、摘要漂移和不干净检出。
2. 使用合成模型/证据的 108 格排程及小规模完整运行回归，证明三策略走同一模型配对与场景合同，规划器路由、归档、恢复、报告及 partial 入口可工作；计划拒绝与提交拒绝分别计数。
3. 实验版 preflight 增加规划器模型可见动作工具→收据/verdict→终态输出的**独立兼容探针**。现有泛用结构化输出探针通过，不足以证明该循环可用；探针失败即停，不生成测量格。
4. 规划器失败的 provider 传输诊断目前没有与 Kernel 同等的归档事件；**冻结前必须**补上脱敏、可严格重载的诊断，并用合成异常覆盖连接、超时、HTTP 状态及非传输错误。否则实验不具备对称的传输敏感性分析，不进入冻结。不得从 `MODEL_ERROR` 或请求计数猜测传输故障。

## 3. 冻结赛程与比较对象

纳入现有 `FORMAL_SCENARIO_IDS` 的 12 个 dev 场景：五组 A/B 故障及两个健康对照。按合同期望预先分层为可确认 5、不足 5、健康 2；不按模型结果重分组。每个场景、每个策略重复 3 次（repeat 1–3），所以规划器 36 格、Kernel 36 格、Static 36 格，总计 **108 个 model-backed 格**、规划器对 Kernel **36 对**。四个 T12 dev 扩展变体不进入主赛程；它们已用于规划器脚本开发，留作另行批准的描述性检查，不能充作 holdout。

一个冻结清单、一次完整 preflight、一次完整 run，不用 selector。对每个 repeat 沿用 v1 的场景轮换位移 `0/4/8`；每个场景内三策略连续执行，策略次序依 repeat 轮换：

| repeat | 单场景内次序 |
| --- | --- |
| 1 | Planner → Kernel → Static |
| 2 | Kernel → Static → Planner |
| 3 | Static → Planner → Kernel |

此顺序使每个策略各占一次三格中的先/中/后位置，但不消除时间相关性；报告必须按 repeat 和实际序号展示结果。配对键为 `(incident_case_id, repeat_index)`，只比较同键的规划器与 Kernel；Static 同键另列，不借用别的场景或旧归档样本。所有三策略绑定 `openai-compatible / deepseek/deepseek-v4.1-flash / https://api.commandcode.ai/provider/v1`，空 `settings_overrides`，与最新正式测量所用模型配对一致；冻结时再核对服务配置与用户的 Goat 套餐可用。基础预算逐格均为 8 次模型请求、8 次取证尝试、2 次提交拒绝、300 秒；规划器另有独立的 2 次计划拒绝预算，分别报告，不合并。

逻辑模型请求的赛程上界为 `108×8=864`，另加实验 preflight 探针实际用量；这是 harness 计数上界，**不是**底层 HTTP 尝试数或费用上界。仅用现有套餐，额外付费上限 0 USD；如服务要求套餐外付费，停止并请 owner 裁定。

## 4. 预登记指标与判读

**主结果**：每格 `EvaluationResult.status == PASSED` 且所有适用 controller 门通过，逐策略报告 `成功/36`，并列 36 对的 `both / only Planner / only Kernel / neither`。主差值为 `only Planner − only Kernel`；模型协议错误、预算耗尽和可归因的传输失败保留在原配对与主分母中，不能只删除失败臂。三个预设层各自报告 `成功/15`、`成功/15`、`成功/6` 与配对四格表。

**筛选判据**（不是显著性检验，也不自动采用）：全 108 格终态且身份/归档/重评分与恢复核对通过后，若规划器相对 Kernel 的净胜至少 **4/36**（约 11 个百分点）、三个预设层的通过数均不低于 Kernel、且不足与健康层的错误确认格数合计不高于 Kernel，则记为“值得另行确认的正向信号”。净胜 ≤0 记为“未见正向信号”；其他情况记为“混合结果”。无论哪类，本轮都不将规划器设为默认策略，不为改判事后追加样本。Static 仅作次对照，不参与此判据。

**完整性/不可判**：任一格未终态、环境或恢复失败、身份/产物不一致、evaluator 逐格重算不一致、`GATE_INTERNAL_ERROR`，均停止并只出部分结果，不给正向筛选结论。若有可靠脱敏 trace 证明 Planner 或 Kernel 一侧的 `CONNECTION_ERROR`、`TIMEOUT` 或 HTTP 5xx，则额外给出**成对**移除的敏感性计数；HTTP 429 单列配额/限流，不自动归为 5xx。无法归因的一侧保留在主结果并列为“来源未定”，不得猜测排除。可归因传输故障对超过 36 对的 25%（即 >9 对）时，实验结果记为不可判；敏感性口径永不替换主结果。

**次指标**：按 T07 既有定义给出状态混淆、合格弃答、逐 claim 支撑和引用质量，注明适用集合/分子/分母；按 T08 只对每个场景×策略×冻结身份的完整 3 次组计算 `pass^1–pass^3`。另列 MODEL_ERROR 原因、工具/请求/输出重试/耗时和 token；规划器归档重建的 STEP/CLOSE/STATE、计划拒绝码与次数、执行步骤、SATISFIED/REVOKED/OPEN、未被最终诊断覆盖的已满足义务。`PlanVerdict` 不能冒充真实 `ToolReceipt`；“拒绝少”或“工具少”本身不是成功。

## 5. 停止、放行与交付

沿用产品内规则：累计至少 12 个终态 model-backed 格后，最近 12 格中至少 10 格未通过，则**下一格启动前暂停**；恢复失败、setup 错误、身份或归档异常立即停。暂停的前缀只作部分分析，不外推 108 格通过率、不算缺失组的 `pass^k`；同身份续跑若窗口仍满足停止条件会再次暂停，不能绕过或另造身份补样本。任何重试或新实验另行裁定。

**第一道放行：实现与离线冻结。** 本设计获实施批准后，完成 §2 的合同和测试、准入/摘要核对与代码影响相称的 unit + integration/归档链路验证；测试 `benchmark verify` 旧清单不退化。依既有 X→Y 纪律，在包含全部最终代码/合同的 X 修订上用官方命令冻结实验清单，仅提交清单得到 Y；独立干净 checkout 的真实检出门、清单字段、108 格与策略身份逐项验收。期间没有真实模型请求、正式数据库测量或历史产物改写。实验 preflight 自身属于第二道。

**第二道放行：真实执行。** owner 另行批准该清单摘要后，在 Y 的干净 worktree 准备 PG/dbt/F0 与进程级密钥环境；执行一次完整 preflight（含规划器专用探针），通过后一次完整 run。保留 doctor 回执、ledger、六文件、scoring-inputs、恢复结果和原始 trace；结束后严格加载、逐格 evaluator 重算、核对 F0、运行 §4 的预登记脚本并写结果报告。preflight 失败即停，不转而运行 suite；测量前不追加规则、prompt 或评分修补。报告代码/文档提交放在**执行 checkout 之外**，不破坏冻结检出门。

交付为：实验 manifest 与完整性报告、108 格逐格及 36 对表、分层主/敏感性指标、T07/T08 和计划轨迹诊断、停止事件与环境/传输清单、所有判据逐项结论。结论须写明所有场景均为 dev、规划器额外策略门、不同政策身份，以及本轮仅用于筛选后续确认研究。
