## 1. 总体判断

应优先改善“能否准确解释实验结果”，随后改善“Agent 能否做对”，最后扩展接入和场景。继续围绕少数失败格追加提示，无法解决评测输入不能完整复现、场景可解性缺乏统一证明、跨次稳定性不清楚这些问题。

完整路线分六个阶段、十四项任务。前四阶段形成可独立交付的评测平台核心；后两阶段扩展策略研究、第三方接入与跨任务数据栈。长期扩展保留在计划内，但不反向阻塞核心交付。

主要依据是 [开源调研 R1](../reports/2026-09-15-open-source-landscape-research.md)，并结合 [修复周期收口 R2](../reports/2026-09-12-kernel-diagnostic-repair-cycle-summary.md)、[24 格比较 R3](../reports/2026-09-12-kernel-static-24-cell-comparison-result.md)、[确认路径回放 R4](../reports/2026-09-12-seq2-confirmation-path-replay-verification.md)、[schema 边界 R5](../reports/2026-09-12-schema-citation-boundary-verification.md)、[收据规划实验收口 R6](../reports/2026-09-12-receipt-planning-experiment-closure.md)。

本计划采用报告中的设计问题，不把报告内标注“转述”的外部实现细节视为已验证事实。选定外部库、协议版本或复用源码时，再核对上游官方文档、许可证与固定版本。

## 3. 目标架构与不变量

数据流：`场景管理与环境验证 → 公开任务视图 → 策略适配器 → 只读工具 → 诊断与轨迹归档`；独立评分器另读私有场景和环境证明。归档之后，评分和报告可以脱离模型、数据库及 dbt 再执行。

新增职责分四层：

1. **任务层**：私有场景合同、公开任务视图、可观测性论证、冻结身份。
2. **执行层**：内置或外部策略、统一预算与 run scope、六工具的受控调用。
3. **证据层**：原始六文件 bundle、受限评分附件、回放夹具与来源摘要。
4. **评测层**：确定性评分、版本间差异、弃答与可靠性统计、实验有效性裁定。

所有阶段遵守：

- 诊断平面只读；管理连接、注入器、任意 SQL、Shell、任意文件读取均不交给策略。
- `ScenarioSpec`、期望根因/状态/资产/缺口矩阵，以及含 expected 字段的评分产物，均不得进入策略输入。现有 `metadata.json` 也含期望信息，不能整体公开给第三方 Agent。
- evaluator 保持独立，不以 kernel 是否接受代替评分，不用 LLM judge 替换主要正确性裁判。
- 原始六文件、旧 manifest、ledger、旧报告不覆写。新附件与新评分使用新身份和独立目录。
- 历史无效批次维持无效；保留已有 `CLOSED / INVALID_HARNESS / NOT_ESTABLISHED` 边界及各协议自己的结果词表，不把不同层级状态揉成单一枚举。
- 离线回放证明软件行为或可达路径，不证明真实模型会选择该路径。
- 预算与策略行为改变必须形成新实验身份。自动探针、代填声明、替模型裁定缺口均不是“接口小修”。

## 5. 任务设计与验收

### T01：建立改进版合同与版本迁移决策

**交付**：新增设计说明与 ADR，列明公开/私有字段、原始结果/派生结果、评分/运行版本、旧协议/新协议边界；批准实施时再修改权威需求对应章节。

**落点**：`docs/requirements.md`、`docs/superpowers/specs/`；对照 `artifacts.py`、`benchmark_manifest.py`、`scenarios.py`。

**决策建议**：保留旧六文件目录布局，增加独立的受限评分附件与派生评分目录；新的通用实验协议独立版本化，不放宽旧 P1 固定排程验证器。

**验收**：每个新增字段标明消费者、来源、是否公开、版本与缺失处理；旧读者继续读取旧产物；任何改变历史评分语义的规则均可明确定位到新版本。仅写一个总版本号不算完成。

### T02：持久化可重评的完整输入

**交付**：拟新增 `evaluation_inputs.py`，定义冻结的 `EvaluationInputBundle` 与严格加载器。

内容包含原始六文件摘要、精确私有 `ScenarioSpec` 快照、`ScenarioVerification`、有来源的恢复证明、策略及预算身份、可恢复的 `DiagnosisRunResult`、schema 版本、原 evaluator 身份。kernel state 从归档的类型化终态事件恢复并验证，不能仅凭 diagnosis 重造。

附件建议存放在 `.dig/scoring-inputs/<run_id>/`，含内容索引；如需迁移或发布，导出受限归档包。文件路径本身不是安全边界，隔离要求见 T11。恢复状态有值但无来源时，不能伪称已保存完整环境证明。

**落点**：`evaluation_runner.py`、`artifacts.py`、`lab_verifier.py`、`benchmark_archive.py`，新增加载器及测试。

**验收**：

- 新运行的所有评分输入可序列化后恢复；同一输入得到相同 checks、适用性和总状态。
- 跨 run、错误场景摘要、篡改、重复 JSON key、不支持的 schema、路径逃逸均拒绝。
- 历史产物按“完整可复评／仅可部分分析／不可复评”分类，附原因；不从当前场景或旧 PASSED 布尔值补造私有验证事实。
- 导出包覆盖输入依赖且有摘要；公开策略视图不含该附件。缺失附件不影响旧 bundle 阅读，但不得声称其可完整重评。

### T03：增加只读离线评分与版本差异报告

**交付**：拟新增 `eval score` 与 `eval compare-scores`，复用 `DeterministicEvaluator`，加载经过验证的评分输入。

派生输出建议为 `artifacts/rescores/<run_id>/<score_id>/`，包含 provenance、evaluation、逐 check diff 和报告。`score_id` 由原始输入摘要、evaluator 源码/依赖摘要、评分配置共同派生；时间等记录字段不进入语义比较。evaluator 身份必须对应实际代码，禁止只替换标签。

**版本策略**：先支持当前版本及已保留的可执行版本；未知版本明确失败。历史版本不齐全时，只支持当前版本评分，不承诺旧版本可复现。

**验收**：

- 禁用模型、数据库、dbt、网络依赖的测试中，完整夹具的同版本逐项评分一致。
- 用一个明确规则差异的受控 scorer 版本测试，证明只有对应检查改变，并给出变更来源。
- 重评前后原 bundle、manifest、ledger、报告摘要完全相同；不原地改分、不自动重跑。
- 无效批次可做有标签的离线诊断，不能输出“恢复为有效实验”。输入不完整只出不完整分析，不产生完整 PASSED。
- 新派生分析不走旧正式 reporter 的完整批次入口；旧正式报告语义不变。

### T04：公开证据参考解与私有答案见证分离

**交付**：拟新增 `reference_solver.py`、`scenario_certification.py`，以及逐场景解题证据说明。

保留两种明确身份：

- **私有答案见证**：用于检查场景期望、声明矩阵及 evaluator 是否自洽；可以读私有合同，但不能称为 Agent 基线或公开可解性证明。
- **公开证据参考策略 `REFERENCE_ANALYST`**：只能接收与被测 Agent 相同的 brief、工具定义和公开事实；通过六工具取证，按领域规则选择假设、引用和终态。适配器不传完整 ScenarioSpec，也不按含答案的 case ID 查表。

覆盖 `CONFIRMED`、`INSUFFICIENT_EVIDENCE`、`NO_INCIDENT` 三类。B 场景不仅要提交能过评分的缺口，还要论证至少两种相容解释在允许工具下不能被可靠区分；健康场景需要正向健康证据。

**验收**：

- 当前目录全部预期可答与健康场景有预算内公开证据路径；不足场景有可复核的不可区分性说明、真实收据和完整缺口。
- 参考策略遵守相同 8/8/2/300 基准预算；超预算成功只能标为另一个放宽预算见证。
- 对场景名称、节点/列的允许重命名、干扰证据变换进行测试，防止记答案；隔离验证阻断私有答案访问。
- 参考解失败先分类为参考实现、场景、工具、预算或评分问题，不能一律判为场景缺陷；未解释失败阻止该新场景准入。
- 原始策略级统计不混入该策略；FIXED_RULE 继续保留原定位。

### T05：建设版本化失败回放库

**交付**：扩展既有测试，建立 `tests/fixtures/diagnostic_replays/` 及夹具索引。每份记录来源报告、原始摘要、脱敏方式、协议版本、触发条件和预期行为。

至少覆盖 R2–R6 中的机制：采齐后过度弃答、必要收据未采集、缺口矩阵不全、跨 claim 引用不替代本 claim 义务、规范资产 ID、schema 错关系被 kernel 接受但 evaluator 拒绝、健康前提不足、协议拒绝/工具拒绝/超时的分类。

使用 `FunctionModel` 或既有确定性 stub 驱动真实 runner/kernel；区分原样失败回放与修改提交后的反事实恢复。既有 trace 未留存的 wire payload、模型推理或动态 instructions 不得伪造为历史原文。

**验收**：每个缺陷回归证明失败触发点及最小修正的影响，至少有相邻反例；断言终态、检查码、预算计数和 run scope，只有协议要求时才锁死完整调用顺序。真实模型恢复能力仍单列为未测。

### T06：建立场景准入与未见变体目录

**交付**：场景卡片、认证命令和开发/保留集管理；继续使用固定 Jaffle Shop，不修改 submodule。

卡片包含：故障机制、正常对照、A/B 决定性证据差异、可解性论证、只读路径、预算、合法替代诊断、真值禁区、来源和版本。B 应与 A 保持相似表面症状，同时移除决定性可观测条件，不能靠名字或固定措辞暴露答案。

**验收**：每个新增场景完成 reset/inject/build/verify/recover、公开参考解及反例检查；测试字段重命名、无关干扰、等价证据重排后结论保持应有关系。先选择现有各故障族代表场景验证方法，再覆盖完整目录。

保留集按故障机制/任务结构划分，不只换随机 seed。已经用于提示开发的历史格全部标为开发集，不能重新标为未见样本。公开答案的样本可用于复现，但不能承担防污染评测的作用。

### T07：增加弃答与引用诊断指标

**交付**：扩展报告指标模块；每项带 numerator、denominator、适用集合和零分母原因。保留既有硬 gate。

| 新指标 | 固定口径 |
| --- | --- |
| 可确认场景过度弃答率 | 期望 CONFIRMED 的有效格中，实际 INSUFFICIENT_EVIDENCE 的数量 / 该集合格数 |
| 健康场景过度弃答率 | 期望 NO_INCIDENT 的有效格中，实际 INSUFFICIENT_EVIDENCE 的数量 / 该集合格数 |
| 合格弃答率 | 期望不足的有效格中，终态为不足且整格 PASSED 的数量 / 该集合格数 |
| 弃答 precision / recall | 阳性定义为“应弃答”，预测阳性为不足终态；作为状态指标，与缺口/收据合格率分开 |
| 逐 claim 支撑覆盖 | 适用结构化 claim 中，有合格事实支撑的 claim 数 / 适用 claim 数；未支持类型单列 |
| 引用有效性与冗余敏感度 | 分别衡量引用是否存在且支撑所属 claim，以及移除一条引用是否改变该 claim 的支持判定 |

引用指标仅针对确定性可判定的结构化声明，不宣称自然语言蕴含准确率；替代引用、互补引用和冗余引用必须分别测，移除不影响判定不等于引用错误。不得直接冠名为 ALCE 指标。

`MODEL_ERROR` 不是弃答；在有效试验中计入对应集合的失败分母，并单列错误率。无效环境样本按协议隔离；零分母为 null，不写 0 或 100%。给出期望三态与实际四态（含 MODEL_ERROR）的完整混淆表，避免单指标掩盖失败。

**验收**：小型手工可验算夹具涵盖全弃答、全确认、健康误报、空集合、模型失败和无效环境；不会因增加无意义引用提高硬门通过率；旧指标保持原结果或明确升级版本。

### T08：重复可靠性与比较协议

**交付**：复用 `repeat_index`，新增版本化通用实验规范与稳定性报告。旧 P1 manifest 保持固定排程；更大 n、外部策略或新场景使用新协议，不修改旧身份。

对相同场景、策略、模型设置、预算、工具和 evaluator 的 n 次预定有效重复，成功数为 s：

`pass^k = C(s, k) / C(n, k)`，其中 `n >= k`；`s < k` 时为 0，`n < k` 时为 null。

这里衡量 k 次均成功，不是“尝试 k 次至少一次成功”的 pass@k。例：n=3、s=2 时，pass^1=2/3、pass^2=1/3、pass^3=0。不得跨场景或跨版本凑 n。

默认候选设计为全部合格场景、每策略每场景三次，报告 k=1/2/3；需要更稳估计时另立 n 更大的预定设计。n=3 是最小能力演示，不作为强统计结论的充分样本量。

**验收**：

- 冻结场景集合、比较单位、全部重复数量、执行顺序、预算和失败归类；每次重置环境，无跨 trial 会话或记忆复用。
- 预定组缺失或环境无效时，主组标记不完整，不通过缩小 n、补跑、换格得到更好结果；完整子集分析单列覆盖量。
- 正常策略超时计失败；有独立证据的 provider/环境故障按预定规则处理，不按输出质量归类。
- 所有公式、ID 唯一性、恢复隔离和报告逻辑先用确定性样本验收；历史单次 R3 不生成 pass^2/3。
- 跨场景汇总明确宏平均、纳入组和样本量；置信区间或重采样考虑场景内相关性，不能把重复 trial 全当独立场景。
- 真实比较另行冻结并执行；无模型预算时本任务可以达到“实现验证完成”，不能写“真实可靠性已验证”。

### T09：统一策略接入协议

**交付**：拟新增 `strategy_adapter.py`，定义公开 task context、工具请求、最终提交、取消和错误信封；内置策略通过薄适配器接入。

harness 统一保管 run ID、白名单、预算、时限与 trace；第三方自报成本/计数只作辅助。外部策略可以用自己的规划循环，但不能自行跳过证据登记或更换 evidence ID。

**验收**：内置适配前后同一确定性输入的诊断、计数与检查结果等价；外部脚本客户端完成确认、弃答、健康三条路径。申报框架、模型、额外工具和可见上下文；能力不相同的策略不标作严格同条件对照。

### T10：开放六工具的 MCP 入口

**交付**：拟新增 `mcp_server.py`，先提供本机 stdio 接入与最小客户端示例；工具名、入参和结果映射到现有证据工具。

只暴露六个业务工具；最终提交走 T09 的独立协议。按组启用是能力收窄，不得绕过场景或策略白名单。每次返回保留 run scope、evidence ID、错误码与真实拒绝收据。

**验收**：与原工具适配器逐项验证结果等价；错误 run、未知关系、超预算、超时、重复调用、断连、并发请求不绕过计数与状态约束。单 run 可串行化保证确定性，不以提升吞吐为由引入跨 run 污染。

SDK 在实施时根据官方文档选定并锁版本；本计划不承诺某个未核对版本的 API。服务不提供 dbt CLI、写 SQL、管理命令或通用文件系统能力。

### T11：外部接入的隔离与可复现验收

**交付**：受限运行配置、公共任务包、确定性外部策略示例、接入说明和端到端验收。

关键隔离对象包括 `config` 中的私有场景、`.dig` 评分附件、含 expected 的 metadata/evaluation/report，以及管理环境变量。使用独立进程/容器与白名单挂载；MCP 协议本身不构成沙箱。只能运行在同仓库且能读答案的外部 Agent 应标为可信开发模式，不用于无泄漏比较。

**验收**：客户端尝试读取真值、其他 run、管理凭据或写数据库时失败且有审计；证据中嵌入要求泄漏答案/修改数据的指令时，权限边界仍成立。确定性攻击夹具通过仅证明边界行为，不等于真实模型抗注入能力已获验证。

Windows 启动与至少一种隔离执行配置均给出实际验证结果；Docker 不可用时如实记环境验收未完成。演示与回放数据可以随仓库发布，保留集答案和敏感附件不随公共任务包发布。

### T12：独立规划策略研究，停止零散提示补丁

**交付**：以新策略身份试验“公开证据义务规划器”，保留原 kernel/static 作为对照。

候选方案由模型提出调查计划，确定性层仅依据公开规则校验依赖、已采证据、剩余预算与真实收据，模型仍负责假设判断、是否继续采证和最终结论。若要自动执行探针或自动补声明，必须单独定义为另一种策略并更新行为合同，不能偷偷进入原 controller。

**验收**：在 T05 回放库与 T06 未见变体上检验引用补齐、收据规划、拒绝后重判和过度弃答；不会读取私有缺口矩阵、自动抬高预算或把健康拒绝当事故证据。软件行为先离线完成验收；真实收益只由 T08 的新冻结比较判定。

比较计划预先确定主指标为整格通过率，并分开报告合格弃答、过度弃答和成本；不把“拒绝次数减少”视作成功。没有收益也可完成研究交付，结论是保留现状或不采用候选方案，不为追求正结果续跑。

### T13：增强可公开验证的 schema 证据

**交付**：先设计可信列映射/类型期望的公共证据合同，再考虑可选工具或工具结果新版本。

候选来源为运行绑定的 dbt manifest、经审核的列级 lineage/模型元数据及可信健康基线；禁止从私有故障定义生成“公开证据”。若 SQL 解析不可靠，则返回显式 UNKNOWN，不能用错误文本或列名相似度猜映射。

**验收**：覆盖列改名、CTE 别名、多上游连接、同名列和未知映射；证明正确引用不被误拒，错误关系能在有充分证据时识别，未知情况仍保留不确定性。

新证据会改变 A/B 可答性，须重新认证相关场景和建立新任务身份。旧六工具场景与旧 NoSchema 消融不迁移到新证据而沿用旧结果。若不能建立可靠公开依据，交付负面结论并保留 R5 边界，不强行新增门禁。

### T14：标准事件映射与跨任务纵切

**交付**：先做现有 run/evidence 到标准事件的单向导出，再做独立的 Airflow + OpenLineage/Marquez 场景包；对接版本和字段在实施时回源核对。

不要将 `Open/Acknowledged/Resolved/Muted` 这类事件管理状态替换诊断的三态。新增生命周期信息独立建模；标准事件缺失本地字段时显式扩展，不能丢失 run ID、来源或证据摘要。

首个跨任务场景建议为“上游晚到导致下游数据不完整”，配套 SLA 内正常迟到、超过窗口的真实事故和缺乏 watermark 的不足变体。管理平面负责启动/注入，诊断平面只读历史和事件。

**验收**：一个完整纵切包含重置、注入、正反对照、参考解、真实来源证据、独立评分、恢复和离线回放；不要求先接多个平台。该新包不得改变固定 Jaffle Shop 基准的旧统计口径。

自动修复、生产告警接管、通用聊天 UI、RAG、多 Agent 产品架构不属于本轮目标；即使时间充足，也不能替代诊断评测可信度的建设。

## 6. 验证与交付纪律

各任务先跑影响范围内的 unit 回归；跨工具、数据库、dbt、归档边界时补对应 integration/e2e。阶段集成时运行相关合并集合，跨层交付或明确发布验收才跑完整非真实模型集合，避免每个小任务重复整套服务测试。

建议发布前检查：

```powershell
uv run ruff check .
uv run pytest tests/unit -q
uv run pytest tests/integration -q
uv run pytest tests/e2e -m 'not real_model' -q
uv lock --check
uv build
git diff --check
```

实际执行报告必须写明 HEAD、改动范围、已运行检查、未运行检查及原因。旧报告中的测试数字不能用于验收新快照。离线测试明确断言不调用模型；不运行含模型探针的 Doctor 来代替离线检查。

阶段交付分开记录三件事：**实现是否完成、环境是否验证、真实模型行为是否测量**。未做真实测量不阻止离线平台功能交付，但不能据此宣布诊断能力提升。

实施授权、需求合同修订、Manifest 生成/证据打包、真实模型或正式 benchmark、提交与推送按对应授权分别执行。本次计划没有执行这些操作，也没有修改旧协议和历史结论。

## 7. 最终完成定义

核心平台完成指 A–D 阶段全部达到：

1. 新产生的完整诊断可以断开模型与数据库重评分，旧结果保留，版本差异可追溯。
2. 进入新评测目录的每个场景有公开可解或必要弃答论证，参考策略不能接触私有答案。
3. 已知失败机制可离线回放，统计可以分清模型决策、工具/接口、场景与环境问题。
4. 过度弃答、合格弃答、引用支持和 pass^k 均有确定分母及手工可验算测试。
5. 第三方确定性 Agent 可通过隔离入口完成受预算约束的诊断和独立评分。

完整路线完成还需 E–F 阶段给出研究结果和一个跨任务纵切；其中研究结论可以是“不采用”，但必须有预先定义的问题、验证材料和适用边界。真实模型效果保持独立验收项，不能靠软件测试宣布完成。

**建议首先实施 T01–T03，形成可信离线重评闭环；随后推进 T04–T08，再开放外部接入。** 这条顺序首先提高后续每一次改动与实验的解释力，同时保留项目现有只读、独立评分和冻结证据的优势。
